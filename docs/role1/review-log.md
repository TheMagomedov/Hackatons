## Что учтено в AI-адаптере

- Источники передаются как SourceInput с bytes, а не локальный путь.
- Fact.text / tone / constraints / assumptions / questions берутся из текущей модели.
- TextDraft использует image_brief / used_source_ids и лимиты подписи Telegram.
- Backend добавляет к запросу верхнюю границу количества постов; она не должна
  подменять явно запрошенное пользователем количество.
- selected_post_id приходит из контекста; AI не выбирает другой пост сам.
- В production постоянные ID, состояние профиля и новые версии создаёт backend.
- Фабрика не делает сетевых запросов; runtime закрывает провайдер.
- После принятия PR #4 обновлён интеграционный тест: использует revision из backend,
  проверяет новую версию и снятое согласование, не предполагает шаг +1.
- Прямого merge альтернативных bootstrap-веток не выполнялось.

## Выполненные проверки

Windows, Python 3.13.9, закреплённые backend зависимости и pypdf 7.0.0:

- Полный pytest на main 38297fa с AI-модулем: **296 passed, 2 skipped, 105 subtests passed**.
- 88 тестов роли 1: источники, клиент, провайдер и интеграция с реальной SQLite.
- Два пропуска — существующие проверки symlink: Windows не разрешает создание ссылок
  без Developer Mode/повышенных прав; системные настройки не менялись.
- Ruff: все проверки пройдены; `git diff --check`: замечаний нет.
- `python -m app demo`: успешный офлайн-цикл, внешних запросов 0.
- Smoke с HTTP-моком: описание кофейни → профиль → три темы → один черновик.
- Интеграция с BackendService: источник → подтверждение профиля → задание на один
  пост → новая редакция → прежнее согласование снято; публикаций не было.

Реальный AI API не вызывался: ключ и модель ещё не настроены. Проверка качества
конкретной модели и её доступа остаётся отдельным live smoke после настройки.
Обычный CI backend не устанавливает pypdf; PDF-specific проверки в нём будут
пропущены до согласования зависимости. Локально PDF-тесты выполнены с парсером.
