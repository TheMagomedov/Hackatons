# Передача backend участникам 1, 3 и 4

Проект: автономный AI-маркетолог. Репозиторий:
`https://github.com/TheMagomedov/Hackatons.git`.

Задача backend — надёжный цикл «материалы → профиль → очередь подготовки →
предпросмотр → согласование конкретной версии → публикация по времени → отчёт».
AI самостоятельно готовит материалы; публикация требует отдельного действия
владельца. Этот документ фиксирует границы модулей и договорённости интеграции.

## 1. Владение кодом

| Роль | Область | Результат |
| --- | --- | --- |
| №1, ML/AI | `app/ai/`, собственные тесты | AIProvider: источники, профиль, намерение, план, текст, правки |
| №2, backend | `app/core/`, `app/storage/`, `app/scheduler/`, `app/publishing/`, `app/shared/`, конфигурация и запуск | Хранение, версии, согласования, очередь, расписание, публикация, общая сборка |
| №3, Telegram/UI | `app/bot/`, собственные тесты | Диалог владельца, загрузка материалов, предпросмотр, callbacks, события реакций |
| №4, изображения/аналитика | `app/media/`, `app/reports/`, собственные тесты | ImageProvider и ReportProvider |

Пути ролей №1, №3, №4 зарезервированы для этих участников. Backend не подменяет их
готовыми production-реализациями. Офлайн demo-провайдеры нужны для проверки общей
сборки и не являются результатом работы настоящих AI/image сервисов.

Не создавайте параллельные модели Post/Business, ещё одну SQLite-базу, scheduler или
альтернативную функцию публикации. Разные Git-ветки не устраняют логические
конфликты: изменение `app/shared/`, зависимостей, конфигурации и запуска согласуется
с №2 до использования нового интерфейса другими модулями.

## 2. Что читать перед реализацией

1. `app/shared/models.py`: Pydantic-модели, ограничения и enum статусов.
2. `app/shared/ports.py`: точные интерфейсы провайдеров.
3. `app/shared/errors.py`: безопасные доменные ошибки.
4. `app/core/service.py`: публичная граница приложения.
5. `docs/TELEGRAM_INTEGRATION.md`: руководство для UI и примеры вызовов.

В проекте пока нет поля/константы `API_VERSION`. Контракты считаются согласованной
границей команды и изменяются через reviewed PR с одновременным обновлением
реализаций, тестов и этих документов. Нельзя молча добавлять обязательное поле или
переименовывать метод в своей ветке.

Общие модели имеют `extra="forbid"` и `frozen=True`: неизвестные поля запрещены,
прямое присваивание полей не используется. Возвращайте валидные модели из
`app.shared.models`. Backend дополнительно валидирует внешние результаты.

## 3. Подключение через фабрики

Договорённые точки подключения runtime:

| Переменная окружения | Фабрика | Сигнатура и результат |
| --- | --- | --- |
| `AI_PROVIDER_FACTORY` | `app.ai.provider:build_provider` | `build_provider(settings) -> AIProvider` |
| `IMAGE_PROVIDER_FACTORY` | `app.media.runtime:build_provider` | `build_provider(settings) -> ImageProvider` |
| `REPORT_PROVIDER_FACTORY` | например `app.reports.provider:build_provider` | `build_provider(settings) -> ReportProvider`, необязательно |
| `BOT_FACTORY` | `app.bot.adapter:build_bot` | `build_bot(service, settings) -> объект с async run(stop_event) и async send(notification)` |

Это синхронные фабрики, возвращающие экземпляры; сеть и длительную генерацию внутри
конструктора/фабрики не запускайте. Один bootstrap создаёт один backend, один набор
провайдеров и один bot adapter. Не запускайте собственный event loop или scheduler
из фабрики. Метод `run(stop_event)` принадлежит только bot adapter; его запуск
координирует общий runtime.

В `Settings`: `ai_factory`, `image_factory`, `report_factory`, `bot_factory`.
Секреты конкретного AI/image-провайдера пока не стандартизованы общими Settings.
Их названия и способ загрузки согласуйте с №2, внесите пустые примеры в
`.env.example`, не добавляйте реальные значения. `Settings` запрещает неизвестные
поля, поэтому нельзя просто передать ему произвольный API key аргумент.

`APP_MODE=demo` означает полностью локальное выполнение без настоящего Telegram,
языковой модели, скачивания сайтов или платной генерации картинок. `APP_MODE=live`
требует явной настройки токена Telegram и фабрик AI/image. Наличие фабрики в
настройке не доказывает её работоспособность: проверьте интерфейс и тестовый вызов
без публикации до общей live-демонстрации.

`OWNER_TELEGRAM_ID` — единственный владелец текущего MVP. Это не многопользовательский
SaaS: не обещайте поддержку нескольких независимых клиентов без расширения прав,
изоляции и тестов.

Для реальной работы явно укажите `DATA_DIR=var/live`, для постоянного demo —
`DATA_DIR=var/demo`. Новая база привязывается к режиму и владельцу до запуска
провайдеров; уже записанную привязку нельзя изменить через `.env`. Схема v1
мигрирует в v2, но непустая старая база без привязки требует отдельного принятия.
Сначала остановите приложение и сохраните весь каталог данных. Затем проверьте
`python -m app status --data-dir var/live` и только для подтверждённой legacy-базы
выполните `python -m app adopt-data --data-dir var/live --mode live --owner-id 123`
с реальным ID вместо `123`. Эти команды не читают `.env` и не вызывают провайдеров;
`status` также не выполняет миграцию. Подробный порядок и случаи отказа — в README.

## 4. Участник №1: AIProvider

Реализуйте **все** методы из текущего протокола:

```python
async def build_profile(self, sources: list[SourceInput]) -> BusinessProfile: ...
async def interpret_request(self, text: str, context: dict) -> TaskIntent: ...
async def make_plan(self, profile: BusinessProfile, request: str) -> ContentPlan: ...
async def write_post(self, profile: BusinessProfile, item: PlanItem) -> TextDraft: ...
async def revise_text(self, profile: BusinessProfile, current_text: str, feedback: str) -> TextDraft: ...
```

Импортируйте `SourceInput`, `BusinessProfile`, `TaskIntent`, `ContentPlan`,
`PlanItem`, `TextDraft` из `app.shared.models`.

### 4.1. Источники — метаданные и bytes, не файловые пути

`SourceInput` содержит:

- `source: Source` — id, business_id, kind, name и соответствующие поля источника;
- `content: bytes | None` — содержимое сохранённого PDF, если источник файловый.

Для `kind="text"` используйте `item.source.text`; для `kind="pdf"` —
`item.content`; для `kind="url"` — `item.source.url`. `asset_id` идентифицирует
ресурс backend, но не является локальным путём. AIProvider не получает `FileStore`,
не открывает SQLite и не ищет файл на компьютере разработчика.

Пример маршрутизации внутри AI-модуля:

```python
for item in sources:
    source_id = item.source.id
    if item.source.kind == "text":
        text = item.source.text or ""
    elif item.source.kind == "pdf":
        if item.content is None:
            raise InvalidInput("Не получено содержимое PDF.")
        text = extract_pdf_text(item.content)  # Ваша реализация.
    else:
        text = await fetch_public_page(item.source.url)  # Ваша реализация.
    # Сохраняйте source_id рядом с извлечёнными фактами.
```

Сканы без текстового слоя, зашифрованные документы и недоступные страницы должны
иметь понятный результат: вопрос пользователю или безопасная ошибка. Не сообщайте
об успешном чтении пустого документа. Ограничивайте страницы, размер извлечённого
текста и длительность разбора. Тяжёлый синхронный парсинг не должен блокировать
общий asyncio event loop.

### 4.2. Безопасное получение публичной страницы

Backend делает только предварительную синтаксическую проверку URL и **не содержит
готового crawler/fetcher**. Участник №1 реализует загрузку одной публичной страницы.

При фактическом запросе повторно проверяйте схему, hostname, порт и отсутствие
учётных данных в URL. Разрешайте только публичные HTTP(S) адреса. До соединения
проверяйте DNS-ответы: loopback, private, link-local, reserved и иные непубличные
адреса нельзя запрашивать. Проверка имени до DNS недостаточна.

Редиректы обрабатывайте с небольшим лимитом и повторной проверкой каждого нового
адреса и его DNS. Не включайте бесконтрольный `follow_redirects=True`. Исключите
DNS rebinding/повторное разрешение на непубличный IP между проверкой и соединением
с помощью контролируемого транспорта или эквивалентной гарантии. Добавьте timeout,
ограничение размера ответа и проверку допустимого содержимого. Не переносите
авторизационные заголовки между хостами.

Тексты страницы и документов — данные бизнеса. Инструкции внутри них не могут
менять системные правила, получать секреты, одобрять пост или вызывать публикацию.

### 4.3. Что возвращают методы

- `BusinessProfile`: название, описание, продукты, аудитория, tone, constraints,
  facts, assumptions, questions. Подтверждённые сведения и предположения разделяйте.
  У фактов указывайте реальные `source_ids` из входа; backend отвергает неизвестные ID.
- `TaskIntent`: только `prepare`, `revise_text`, `revise_image`, `report`, `clarify`.
  `context` содержит `business_id` и `selected_post_id`. Не придумывайте другой
  post_id. Распознавание намерения — рекомендация UI, а не согласование.
- `ContentPlan`: от 1 до 5 `PlanItem`, но запрос backend задаёт более строгий
  `MAX_POSTS_PER_JOB` (по умолчанию 3); соблюдайте этот лимит. У каждого элемента
  заполните topic, goal, brief, image_brief. suggested_at — aware datetime или None.
- `TextDraft`: непустой text до 900 Python-символов и не более 1024 UTF-16 units;
  image_brief, used_source_ids, warnings. При emoji лимит UTF-16 проверяется отдельно.
  Текст публикуется как plain text; HTML/Markdown-разметка не выполняется.
- `revise_text` возвращает полный TextDraft новой редакции. Версию и статус поста
  назначает backend; AIProvider не изменяет их. До вызова вашего метода backend
  уже резервирует пост в `editing` и снимает старое согласование. При ошибке
  возвращайте безопасное исключение: пост останется без согласования в `failed`,
  автоматического платного повтора или отправки старой версии не будет.

Не возвращайте «почти JSON» без валидации или бесконечно исправляйте его повторными
вызовами модели. Ограничьте попытки, стоимость и длительность. При неудаче выдайте
безопасную `ProviderUnavailable`/`InvalidInput` без сырого provider response.

Проверки перед передачей: неизвестный source ID, отсутствие цены, инструкция
«игнорируй правила» внутри PDF, недоступная страница, редирект в localhost,
невалидный structured output, длинный caption с emoji, попытка AI одобрить пост,
правка текста с сохранением подтверждённых фактов.

## 5. Участник №4: ImageProvider

```python
async def generate(
    self,
    profile: BusinessProfile,
    text: TextDraft,
    feedback: str | None = None,
) -> GeneratedImage: ...
```

Вход содержит стиль бизнеса, полный текст и `text.image_brief`. При правке backend
может передать `feedback` отдельно. Текущий контракт не передаёт предыдущую картинку:
это повторная генерация с пожеланиями, а не гарантированное редактирование пикселей
старого изображения. Если требуется настоящее image editing, сначала согласуйте
новый контракт.

Возвращайте `GeneratedImage`:

```python
return GeneratedImage(
    content=image_bytes,
    mime_type="image/png",  # либо image/jpeg
    provider="имя-реального-провайдера",
    is_demo=False,
)
```

Разрешены PNG/JPEG, от 1 до 10 000 000 bytes, MIME должен соответствовать сигнатуре.
Возвращайте байты, а не URL, путь на рабочем столе, base64-строку или Telegram file_id.
Если провайдер вернул URL, получением результата в bytes занимается ваш модуль с
контролем размера и timeout. Backend сохраняет ресурс, выдаёт Asset.id и назначает
новую версию поста.

Проверяйте, что получен реальный пригодный файл, а не HTML ошибки под видом PNG.
Ограничьте разрешение/формат в соответствии с выбранным способом публикации.
Тестовые картинки маркируйте `is_demo=True`. Live backend и live publisher
запрещают публикацию demo-материалов. При недоступности реального провайдера нельзя
молча возвращать заглушку с `is_demo=False`.

Проверки: успешная генерация, ошибка/timeout, пустой файл, неверный MIME, слишком
большое содержимое, изменение по feedback, маркировка demo, безопасные исключения.

## 6. Участник №4: ReportProvider

```python
def build(self, data: ReportInput) -> str: ...
```

Это синхронный метод. Внутри не запускайте сетевой вызов AI или event loop.
Для MVP сформируйте отчёт обычным Python по реальным данным. Если позднее нужен
асинхронный AI-комментарий, изменение протокола согласуется отдельно.

ReportInput содержит `business_id`, `start`, `end`, `posts`, `metrics`:

- Интервал данных включительный: `[start, end]`.
- `posts` содержит все посты бизнеса, включая созданные до периода. Фильтрацию
  выполняет reporter по смыслу показателя: подготовлено — по created_at,
  опубликовано — по published_at.
- Статусы постов являются текущими снимками. Они не дают полную историю согласований
  или состояние на прошлую дату. Не выводите «согласовано за период» по текущему
  `status=approved`; можно явно показать «сейчас ожидают/согласованы».
- `metrics` содержит снимки внутри периода и последний снимок строго до start
  для каждого потока `(name, post_id, source)`. Этот предыдущий снимок — baseline.
  Будущие снимки после end не включаются.

Подписчики и реакции — значения счётчика в момент измерения, а не слагаемые.
Не суммируйте число подписчиков за все дни и не складывайте повторные снимки
реакций одного поста. Для изменения сравнивайте подходящие начальный и конечный
снимки одного потока, показывая время измерений. Если baseline отсутствует,
прирост неизвестен; не подменяйте его нулём. Разницу реакций можно наблюдать и
отрицательную, если реакции удалены.

Данные с `source="demo"` и `post.is_demo=True` явно обозначайте. Не объединяйте
реальные и тестовые показатели в одну неподписанную цифру. Для отсутствующего
показателя пишите «нет данных», для измеренного нуля — «0». Охваты, клики, продажи,
конверсия и причинное влияние постов на рост подписчиков пока не предоставлены
контрактом и не должны появляться как факты.

Reporter не читает SQLite, не вызывает Telegram и не получает Repository.
Структурированные данные поступают только через `BackendService.report_data`;
строковый отчёт — через `BackendService.build_report`.

Проверки: пустой период, нулевое измерение, отсутствующий baseline, несколько
снимков одного счётчика, пост создан до периода и опубликован внутри, снимки реакций
для старого поста, demo-маркировка, отсутствие выдуманных показателей.

## 7. Основные вызовы сервиса для участника №3

Подробные примеры находятся в `docs/TELEGRAM_INTEGRATION.md`.

| Операция | Метод | Async |
| --- | --- | --- |
| Создать/получить/список бизнесов | create_business(actor_id, name, timezone=None), get_business(actor_id, business_id), list_businesses(actor_id) | Нет |
| Подключить канал | connect_channel(actor_id, business_id, channel_id) | Да |
| Добавить текст/PDF/URL | add_text_source(actor_id, business_id, text, name=...), add_pdf_source(actor_id, business_id, filename, content), add_url_source(actor_id, business_id, url) | Нет |
| Изучить бизнес | analyze_business(actor_id, business_id) | Да |
| Исправить/подтвердить профиль | save_profile(actor_id, business_id, expected_version, profile), confirm_profile(actor_id, business_id, expected_version) | Нет |
| Распознать намерение | interpret_request(actor_id, business_id, text, post_id=None) | Да |
| Создать задание | request_preparation(actor_id, business_id, request, request_id) | Нет |
| Статус/план/посты задания | get_job(actor_id, job_id), get_plan(actor_id, job_id), get_job_posts(actor_id, job_id) | Нет |
| Посты/изображение | list_posts(actor_id, business_id), get_post(actor_id, post_id), read_asset(actor_id, asset_id) | Нет |
| Правка по замечанию | revise_text(actor_id, post_id, expected_revision, feedback), revise_image(actor_id, post_id, expected_revision, feedback) | Да |
| Ручная правка | edit_post(actor_id, post_id, expected_revision, *, text=None, image_asset_id=None, scheduled_at=None, channel_id=None) | Нет |
| Согласовать/отклонить | approve_post(actor_id, post_id, expected_revision), reject_post(actor_id, post_id, expected_revision) | Нет |
| Автоподготовка | configure_automation(actor_id, business_id, enabled, request=..., interval_hours=24, first_run_at=None) | Нет |
| Отчёт/данные | build_report(actor_id, business_id, start, end), report_data(actor_id, business_id, start, end) | Нет |

`request_id` — стабильный ID Telegram update, не случайная строка на каждую попытку.
`expected_revision` — версия из показанного предпросмотра. Старые кнопки нельзя
«исправлять» подстановкой текущей версии перед согласованием. Время — aware datetime.

При `revise_text`/`revise_image` отображайте состояние `editing`; кнопки согласования
и новой правки для него недоступны. После успеха используйте `updated.revision`
из возвращённого PostView: у одной AI-правки есть резервирование и завершение,
поэтому нельзя вычислять номер как `старый + 1`. При ошибке обновите пост из backend
и покажите `failed`/`last_error`, не возвращайте старое согласование в интерфейсе.

`prepare_next_job`, `publish_due_once`, `schedule_automations`,
`dispatch_notifications`, `collect_metrics`, `recover_interrupted` вызываются
runtime/scheduler, а не обработчиками пользовательских кнопок.

Общий scheduler содержит пять независимых циклов: публикация, генерация,
автоматизация, уведомления и метрики. Собственные циклы других участников не нужны.
Результат операции и нужное уведомление попадают в БД атомарно; доставка outbox
происходит отдельно и может повториться после сбоя. UI показывает состояние
backend и не повторяет генерацию или публикацию вслед за повторным уведомлением.

## 8. Сборка и общие проверки

1. Сначала получите общий backend с `main` и проверьте локальный demo по README.
2. Каждый провайдер разрабатывается на примерах общих моделей и MockTransport,
   без платных вызовов в обычных тестах.
3. №1 подключает AI factory, №4 — image factory. Backend вызывает их существующими
   методами, сохраняет план и создаёт черновики целым заданием.
4. №3 подключает bot factory и проходит весь диалог до предпросмотра.
5. На специально выбранном тестовом канале проверяются права, явное согласование,
   будущая дата, реальная публикация и ссылка. Публикации не должны выполняться
   автоматически при импорте модулей, запуске тестов или создании фабрики.
6. Подключается reporter, проверяются отсутствие данных и реальные измерения.
7. Выполняется прогон с повторным update, устаревшей кнопкой, долгой/неудачной правкой
   после согласования, перезапуском и неизвестным результатом отправки. Во время
   `editing` старая одобренная версия не должна выходить в канал.

Контрольные ограничения: одно приложение/один runtime, один владелец MVP,
одна фотография с plain-text caption, подтверждённый профиль и проверенный канал
перед подготовкой, новое согласование после каждой правки, никаких слепых повторов
публикации, никакого смешения demo и live. Результаты provider не дают полномочий
на изменение состояния или доступ к другим бизнесам.

## 9. GitHub: подключение и Pull Request

Владелец репозитория добавляет каждого участника через Settings → Collaborators →
Add people; приглашённый принимает приглашение под своим аккаунтом. Публичность
репозитория сама по себе не разрешает push в него.

Перед началом интеграции дождитесь принятого PR backend в `main`. Если команда
начинает раньше, №2 должен явно назвать общий базовый commit/ветку: не создавайте
несовместимые копии shared-контрактов в своих проектах.

Пример первой настройки для участника №3:

```bash
git clone https://github.com/TheMagomedov/Hackatons.git
cd Hackatons
git switch main
git pull --ff-only origin main
git switch -c codex/telegram-bot
```

Для №1 используйте `codex/ai-content`, для №4 — `codex/media-analytics`.
Работайте в одном клоне, а не копируйте файлы между несколькими независимыми
папками проекта без Git. У каждого участника собственный клон на его компьютере.

Перед commit убедитесь, что `.env`, реальные ключи, локальная база, загруженные
документы, генерации, venv и кэши не попадают в Git. `.env.example` содержит только
имена параметров и безопасные примеры. Добавляйте конкретные файлы своего модуля.

Пример после создания файлов Telegram-модуля и его тестов:

```bash
git status
git add app/bot/ tests/bot/
git diff --cached
git commit -m "Add Telegram adapter using BackendService"
git push -u origin codex/telegram-bot
```

Затем создайте PR: base `main`, compare ваша ветка. В описании укажите поведение,
изменённые контракты (если согласованы), нужные настройки, выполненные тесты и
известные ограничения. Участник №2 проверяет интеграцию и объединяет PR. Если PR
меняет shared/requirements/runtime, привлеките затронутых участников к проверке.

Чтобы получить уже объединённые изменения в свою ветку, сначала сохраните свою
работу коммитом, затем:

```bash
git fetch origin
git merge origin/main
```

При конфликте в общих моделях не выбирайте автоматически «всё наше» или «всё их».
Согласуйте итоговый контракт, исправьте реализацию и повторите затронутые тесты.
Не используйте force push в общие ветки. После принятого PR следующую независимую
задачу удобно начинать новой веткой от обновлённого `main`.
