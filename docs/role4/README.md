## Генерация изображений

Контракт backend:

```python
async def generate(profile: BusinessProfile, text: TextDraft,
                   feedback: str | None = None) -> GeneratedImage: ...
```

Backend вызывает генерацию до создания постов. Генератор получает профиль,
текстовое задание и правку; возвращает байты одного PNG, MIME, имя провайдера и
`is_demo`. ID поста, ревизию и ID файла назначает backend. Сохранение в `var/`,
согласование, расписание и публикация также остаются за backend.

`app/media` предоставляет подключаемый клиент и адаптер OpenAI Images.
Провайдер и модель пользователем пока не выбраны. Ключ и модель передаются
явно. Принятая командой runtime-обёртка читает `IMAGE_API_KEY`, `IMAGE_MODEL` и
`IMAGE_API_BASE`; низкоуровневая фабрика по-прежнему получает их аргументами.
Без ключа или модели live-обёртка позволяет открыть Telegram-меню и отчёты,
но генерация сообщает понятную ошибку настройки. Модель по умолчанию не выбирается.
Зависимости и поля общего `Settings` ради этого не добавляются.

Сетевой запрос выполняется вне event loop. Ограничены время ожидания, размеры
задания и ответа; проверяются формат, структура и размеры PNG. Редиректы,
автоматические повторы платной генерации и скрытая подмена тестовой картинкой
не используются. Отмена ожидания не гарантирует отмены уже начатой генерации
на сервере. Реальные платные запросы в тестах не выполняются.

Тестовая картинка всегда имеет `is_demo=True`; live backend запрещает её
публикацию. Задание и факты считаются данными, но prompt не гарантирует
безошибочность модели. Пользователь проверяет готовый текст и изображение.
После замены изображения backend запрашивает согласование новой ревизии.
При правке существующего поста backend сначала переводит его в `editing` и
снимает прежнее согласование до ожидания генератора. Успех возвращает `review`,
ошибка или отмена — `failed` без восстановления согласования. Номер новой
ревизии берётся из возвращённого PostView, а не вычисляется как `старый + 1`.
Правка изображения по текущему контракту — новая генерация по feedback:
предыдущие байты изображения в интерфейсе не передаются.

Для точного имени САЛАВАТСТЕКЛО (включая АО) live-фабрика добавляет исходный
логотип и заголовок из уже готовой подписи поверх отдельной белой шапки.
Фотография сохраняется целиком, результат остаётся PNG в прежних лимитах.
Для других компаний и demo результат не меняется. Новая обёртка модерации
backend проверяет готовую карточку; именно проверенные байты сохраняются.
Офлайн QA проверяет сборку этой цепочки, сохранение и отчёт, не качество
ответа внешней модели или доступность её сервера.

Формат адаптера сверяется с [официальной документацией Images API](https://developers.openai.com/api/docs/guides/image-generation).
Примеры и точные настройки находятся в `app/media/README.md`.

## Аналитика и отчёты

Контракт backend:

```python
def build(data: ReportInput) -> str: ...
```

Фабрика `app.reports.provider:build_provider` подключается через уже существующую
переменную `REPORT_PROVIDER_FACTORY`. Reporter получает все текущие посты
одного бизнеса, снимки показателей в период и предыдущие baseline-снимки.
Интервал включительный: `[start, end]`, как в backend. Даты имеют часовой пояс.
Сам reporter не читает БД, не вызывает Telegram и не обращается к AI.

Создания и публикации считаются по реальным `created_at` и `published_at`.
Текущие статусы показываются отдельно: они не дают историю согласований,
ошибок и ревизий. Статус `editing` показывается как «редактируются»; отчёт
доступен и во время ожидания генерации. Подписчики и реакции — снимки счётчиков; повторные снимки
не складываются. Источники и demo-данные разделяются. При отсутствии baseline
прирост остаётся неизвестным. Неизвестные показатели не заменяются нулями.
Просмотры, охват, клики, продажи и конверсия текущим контрактом не предоставлены.

Публичные вычисления и их ограничения описаны в docstrings `app/reports`.
Строковый результат отправляется Telegram-модулем как обычный текст,
с `parse_mode=None`.

## Передача команде

| Роль | Передаёт модулю | Получает |
| --- | --- | --- |
| 1, AI | BusinessProfile, TextDraft с image_brief | Изображение по подтверждённым сведениям |
| 2, backend | Настройки, ReportInput, управление жизненным циклом | GeneratedImage и строковый отчёт |
| 3, Telegram | Feedback через BackendService | Предпросмотр картинки и текст отчёта |

Все новые внешние входы и результаты используют общие модели. Изменения
`app/shared`, Settings, требований и запуска согласуются с ролью 2.

## Проверка

Python 3.12 и зависимости, зафиксированные backend:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.txt
.venv/bin/python -m ruff check .
.venv/bin/python -m pytest -q
.venv/bin/python -m app demo
```

В macOS системный временный каталог может начинаться с `/var`, который
является symlink на `/private/var`. FileStore запрещает ссылки в пути.
Для тестов используйте существующий абсолютный TMPDIR без symlink-компонентов
(например, созданный каталог в рабочей папке) и передайте его через окружение.
Запрет FileStore ради тестов не отключается.

Автоматические проверки уже есть в общей `.github/workflows/tests.yml`;
модули роли 4 включаются в общий pytest/ruff без отдельного CI или зависимостей.
Отдельный офлайн-сценарий проверяет новый AI-адаптер с подставным HTTP-ответом,
наш DemoImageProvider, сохранение PNG в backend и наш reporter. Тестовые
материалы учитываются в demo-группе, внешние измерения не выдумываются.
Сценарии будущей сквозной проверки находятся в [qa-checklist.md](qa-checklist.md),
порядок обзора Git — в [git-workflow.md](git-workflow.md).

Настоящий API изображений и live-диалог Telegram проверяются после выбора
провайдера и заполнения локальной конфигурации. Фабрики соседних модулей уже
подключены командой в `main`; их офлайн-проверка не вызывает внешний API.
Успешные офлайн-тесты не подтверждают готовность этих внешних интеграций.
